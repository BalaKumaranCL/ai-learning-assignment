2. What it reaches: as a stdio subprocess it runs with my agent's OS user, so it can reach anything that user can (files, network, env vars) -- MCP gives it no sandbox; I handed it only a registry token via env, but the stand-in needs nothing beyond its own data file, and the real one should be run in a container with egress allowed to the registry host only.
3. What it logs: every call, with full arguments (package@version asked about), the last 4 chars of my token and the client name, to its own file (see registry_access.log) -- so my users' package queries are visible to its maintainer if logs are shipped, and I can't see what the real one sends off-box.
4. Stolen-token blast radius: a stolen REGISTRY_API_TOKEN lets the thief read version/deprecation data as me (low value, read-only), but a compromised server publish is worse: it can rewrite tool descriptions (prompt-inject my model via tools/list) or return false "not deprecated" answers, so the token should be read-only, short-lived and rotated.
5. Verdict: DON'T SHIP as-is -- ship only behind the gateway (scoped read-only token, audit line per call, tool list pinned/diffed on every start) with the server's source reviewed and version-pinned; until those exist, keep it out of production.
